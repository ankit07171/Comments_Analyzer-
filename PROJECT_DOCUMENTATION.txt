PROJECT OVERVIEW
================================================================================

Project Name: Comment Intelligence Platform
Type: Multi-Platform Social Media Comment Analysis & Automation System
Version: v1.3 (rule-engine + VADER sentiment)
Architecture: Monolithic Streamlit Web Application with External API Integrations

PURPOSE & MISSION:
The Comment Intelligence Platform is an advanced social media monitoring and
automation tool designed to help businesses, content creators, and customer
support teams manage high volumes of comments across multiple social media
platforms (YouTube, Instagram, Bluesky). 

Instead of manually scrolling through hundreds or thousands of comments, this
platform automatically:
1. Ingests comments from multiple social media platforms
2. Analyzes each comment across multiple dimensions (sentiment, emotion, intent)
3. Prioritizes comments based on business risk and urgency
4. Automatically creates support tickets for high-priority negative comments
5. Provides explainable AI - showing WHY each comment was flagged

CORE VALUE PROPOSITION:
- EXPLAINABILITY: Every classification includes the exact phrases that triggered
  it, confidence scores, and human-readable explanations
- AUTOMATION: High-risk comments automatically become Jira tickets
- MULTI-DIMENSIONAL: Analyzes WHAT was said, WHY it matters, WHO said it, and
  HOW urgent it is
- ZERO SERVER SETUP: No Docker, Kafka, or server infrastructure needed

DETAILED WORKFLOW:

PHASE 1: DATA INGESTION
────────────────────────
User Action: Enters a social media URL in the Streamlit dashboard
Platform Options: YouTube, Instagram, or Bluesky

Step 1.1 - Platform Script Execution:
  - Dashboard spawns subprocess to run platform-specific ingestion script
  - Scripts: youtube/fetch_comments.py, instagram/fetch_comments.py, 
             bluesky/fetch_comments.py
  
Step 1.2 - API Authentication:
  - YouTube: Uses YouTube Data API v3 with API key
  - Instagram: Uses Apify Actor API (instagram-comment-scraper)
  - Bluesky: Uses AT Protocol SDK with app password authentication
  
Step 1.3 - Data Extraction:
  Each script extracts:
  - Comment text
  - Author/username
  - Like count (engagement metric)
  - Timestamp (for burst detection)
  - Post metadata (title, views, channel info)
  
Step 1.4 - Data Persistence:
  - CSV file: data/comments_YYYYMMDD_HHMMSS.csv
  - Metadata file: data/metadata_YYYYMMDD_HHMMSS.json
  - Optional: AI summary from Gemini API (if configured)


PHASE 2: MULTI-DIMENSIONAL ANALYSIS
────────────────────────────────────
Location: src/analyzer.py
Method: analyze_dataframe() → iterates analyze_comment() per row


ANALYSIS DIMENSIONS:

Dimension 1: SENTIMENT ANALYSIS
  Engine: VADER (Valence Aware Dictionary and sEntiment Reasoner)
  Method: Lexicon-based sentiment scoring (no ML model required)
  Output: 
    - sentiment: "Positive", "Negative", or "Neutral"
    - sentiment_score: -1.0 (very negative) to +1.0 (very positive)
  Decision Logic:
    - compound >= 0.25  → Positive
    - compound <= -0.25 → Negative
    - Otherwise         → Neutral
    - Exception: Generic short phrases ("ok", "nice") → Neutral

Dimension 2: EMOTION DETECTION
  Engine: Custom keyword lexicon matching
  Emotions Detected:
    - anger: ["angry", "furious", "rage", "pissed"]
    - frustration: ["frustrated", "fed up", "tired of"]
    - joy: ["love", "amazing", "awesome", "best"]
    - fear: ["worried", "scared", "unsafe"]
    - sarcasm_risk: ["yeah right", "sure jan", "totally"]
    - urgency: ["asap", "immediately", "emergency"]
  Output: List of detected emotions + primary_emotion (most phrases matched)

Dimension 3: INTENT CLASSIFICATION
  Engine: Priority-ordered keyword lexicon
  Intents (in priority order):
    1. refund_risk: ["refund", "money back", "chargeback"]
    2. complaint: ["worst", "terrible", "broken", "disappointed"]
    3. support_request: ["how do i", "need help", "not working"]
    4. misinformation_risk: ["fake news", "hoax", "debunked"]
    5. purchase_intent: ["where can i buy", "price", "link please"]
    6. feature_request: ["please add", "wish you had", "suggestion"]
    7. praise: ["love this", "amazing", "best video"]
    8. spam: (detected separately via spam markers)
    9. general_discussion: (default if no match)
  Output: 
    - intent: The highest-priority matched intent
    - intent_confidence: 0.45-0.95 based on match count

Dimension 4: SPAM DETECTION
  Method: Keyword marker matching
  Spam Markers: ["follow me", "check my page", "dm me", "click the link",
                 "free followers", "giveaway", "bit.ly"]
  Output: 
    - is_spam: Boolean
    - spam_score: 0.0-1.0 (weighted by marker count)

Dimension 5: TOXICITY DETECTION
  Method: Toxic keyword matching
  Toxic Markers: ["idiot", "stupid", "shut up", "kill yourself"]
  Output:
    - is_toxic: Boolean
    - toxicity_score: 0.0-1.0 (weighted by marker count)

Dimension 6: PRIORITY SCORING (0-100 scale)
  Algorithm: Additive scoring with business logic
  Scoring Rules:
    +35 points: Toxic language detected
    +25 points: Negative sentiment
    +25 points: Complaint or refund risk intent
    +15 points: Spam markers present
    +10 points: Support request
    +10 points: Urgency emotion detected
    +10 points: Anger or frustration emotion
    +10 points: High engagement (25+ likes)
  
  Priority Levels:
    - Critical: 70-100 points
    - High:     45-69 points
    - Medium:   20-44 points
    - Low:      0-19 points

Dimension 7: EXPLAINABILITY
  Every analysis includes:
    - key_phrases: The exact words that triggered classification (max 6)
    - confidence: Overall confidence score (0.0-0.97)
    - reason_summary: Plain-English explanation of why flagged
    - model_version: "rule-engine-v1.3+vader-3.3" for audit trail
  
  Example reason_summary:
    "Flagged High priority — toxic language (idiot); negative sentiment 
    (-0.654); complaint detected; anger detected."


PHASE 3: MODERATION INTELLIGENCE
─────────────────────────────────
Location: src/simi.py, src/burst.py, src/score.py

Module 1: SPAM SIMILARITY CLUSTERING (simi.py)
  Purpose: Detect coordinated spam campaigns or copy-paste attacks
  Algorithm: TF-IDF + Cosine Similarity
  Process:
    1. Extract all spam-flagged comments
    2. Convert to TF-IDF vectors (removes common words)
    3. Calculate cosine similarity matrix
    4. Group comments with similarity > 0.85 threshold
    5. Return clusters + similarity_score (% of spam that's duplicated)
  
  Use Case: Identify bot networks posting identical promotional content

Module 2: COMMENT BURST DETECTION (burst.py)
  Purpose: Detect sudden spikes in comment activity (brigading/coordinated attacks)
  Algorithm: Statistical Z-score on time-windowed comment counts
  Process:
    1. Parse comment timestamps
    2. Group into 10-minute windows
    3. Calculate mean and standard deviation
    4. Flag windows where Z-score > 2.5 (statistical outliers)
  
  Output: 
    - burst_flag: Boolean (True if suspicious burst detected)
    - burst_series: Time-series data for visualization
  
  Use Case: Detect coordinated harassment or brigading campaigns

Module 3: CAMPAIGN RISK SCORING (score.py)
  Purpose: Aggregate spam similarity + burst detection into single risk score
  Algorithm: Weighted scoring
    - High similarity (>0.3): +40 points
    - Burst detected: +30 points
    - High spam ratio (>15%): +30 points
    - Maximum: 100 points
  
  Output: campaign_score (0-100) + plain-English explanations
  Use Case: Alert community managers to coordinated attacks


PHASE 4: ALERT ROUTING & AUTOMATION
────────────────────────────────────
Location: src/alerts.py

Step 4.1 - Alert Filtering:
  Criteria for alert eligibility:
    - Priority >= ALERT_PRIORITY_THRESHOLD (default: "High")
    - Sentiment = "Negative" OR is_toxic = True
    - Excludes spam-only comments (no Jira ticket for pure spam)

Step 4.2 - Deduplication Check (Redis):
  Purpose: Prevent duplicate Jira tickets when re-analyzing same dataset
  Method:
    1. Generate hash: SHA-256(author + comment text, lowercased)
    2. Check if key "alert:<hash>" exists in Redis
    3. If NOT exists: Create key with TTL = ALERT_DEDUPE_TTL_HOURS (default: 24h)
    4. If exists: Skip (already alerted within TTL window)
  
  Integration: Upstash Redis REST API (serverless, no Docker)
  Graceful Degradation: If Redis not configured, treats all as "new"

Step 4.3 - Optional AI Explanation (Gemini):
  Trigger: Only for NEW alerts (not duplicates)
  Limit: Max 5 AI explanations per alert run (cost control)
  Purpose: Generate natural-language "why this matters" explanation
  Fallback: Uses rule-based reason_summary if Gemini unavailable
  
  Example AI explanation:
    "This comment was flagged because the user is threatening a chargeback
    and using hostile language ('ripped off'), which indicates immediate
    refund risk and requires urgent customer service intervention."

Step 4.4 - Jira Ticket Creation:
  Integration: Jira Cloud REST API v3
  Authentication: Email + API token (from .env)
  
  Ticket Structure:
    Summary: "[Platform] Priority level comment from @author"
    Description:
      - Platform name
      - Author username
      - Sentiment + score
      - Intent classification
      - Priority score (0-100)
      - Full comment text
      - Explanation (AI or rule-based)
    Labels: ["comment-intelligence", platform name, intent]
    Issue Type: Configurable (default: "Task")
    Project: Configurable via JIRA_PROJECT_KEY
  
  Response: Returns Jira ticket key (e.g., "CS-1234") + browse URL

Step 4.5 - Metrics Tracking (Redis):
  Counter: "stats:negative_alerts:YYYY-MM-DD"
  Purpose: Track daily alert volume for dashboard KPI
  Increment: +1 for each NEW alert created (not duplicates)


Step 4.6 - Local Audit Log:
  File: data/alerts_log.json
  Purpose: Persistent record of all alerts (even if Jira/Redis fail)
  Content: Alert metadata, timestamp, Jira result, explanation
  Retention: Last 500 alerts (automatic rotation)

NATURAL LANGUAGE PROCESSING (NLP)
──────────────────────────────────

1. VADER Sentiment Analysis
   Package: vaderSentiment 3.3.2
   Type: Lexicon-based (rule-based, not ML)
   
   Why Chosen:
     - No model training or downloads required
     - Works immediately out-of-the-box
     - Optimized for social media text (slang, emojis, caps)
     - Fast: <1ms per comment
     - Explainable: Uses predefined word-sentiment mappings
   
   How It Works:
     - Maintains dictionary of 7500+ words with sentiment scores
     - Adjusts for: negation ("not good"), intensifiers ("very bad"),
       capitalization ("HATE"), punctuation ("!!!"), emojis
     - Returns compound score: -1 (most negative) to +1 (most positive)
   
   API Used:
     SentimentIntensityAnalyzer.polarity_scores(text)
     Returns: {'neg': 0.x, 'neu': 0.x, 'pos': 0.x, 'compound': -1 to 1}

2. Scikit-learn (TF-IDF for Spam Clustering)
   Package: scikit-learn 1.4+
   Modules Used: TfidfVectorizer, cosine_similarity
   
   Why Chosen:
     - Industry-standard for text vectorization
     - No GPU required
     - Efficient sparse matrix operations
     - Mature and well-documented
   
   How It Works (simi.py):
     - TfidfVectorizer: Converts text to numerical vectors
       - TF (Term Frequency): How often word appears in document
       - IDF (Inverse Document Frequency): Weights rare words higher
       - Automatically filters English stop words ("the", "a", "is")
     - cosine_similarity: Measures vector angle (0=different, 1=identical)
     - Clustering: Groups comments with similarity > 0.85
   
   Use Case: Detecting bot networks posting identical spam

3. TextBlob
   Package: textblob 0.18+
   Status: Installed but NOT actively used in current version
   Potential Use: Spelling correction, noun phrase extraction

EXTERNAL API INTEGRATIONS
──────────────────────────

1. YOUTUBE DATA API v3
   Provider: Google Cloud Platform
   Authentication: API Key
   
   Endpoints Used:
     - GET /youtube/v3/videos
       Purpose: Fetch video metadata (title, views, likes, comment_count)
       Parameters: part=snippet,statistics, id=video_id, key=API_KEY
       Rate Limits: 10,000 quota units/day (free tier)
       Cost per call: 1 unit (metadata) + 1 unit (comments)
     
     - GET /youtube/v3/commentThreads
       Purpose: Fetch top-level comments
       Parameters: videoId, maxResults=100, order=relevance, pageToken
       Pagination: Uses nextPageToken for >100 comments
       Max Retrieved: 1000 comments (configurable limit)
   
   Response Format:
     {
       "items": [
         {
           "snippet": {
             "topLevelComment": {
               "snippet": {
                 "textDisplay": "comment text",
                 "authorDisplayName": "username",
                 "likeCount": 42,
                 "publishedAt": "2024-01-01T12:00:00Z"
               }
             }
           }
         }
       ]
     }
   
   Error Handling:
     - 403: Quota exceeded or disabled comments
     - 404: Video not found
     - 400: Invalid video ID format

2. APIFY API (Instagram Scraper)
   Provider: Apify.com
   Authentication: API Token
   
   Architecture: Actor-based (serverless scraping)
   Actor Used: apify/instagram-comment-scraper
   
   Why Apify (No Official Instagram API):
     - Instagram Graph API requires Business Account + Facebook Page
     - Graph API doesn't provide comment endpoints for public posts
     - Apify handles browser automation, CAPTCHA, rate limiting
   
   API Flow:
     1. POST to actor run endpoint with input JSON
        Input: {"directUrls": [url], "maxComments": 500}
     2. Poll run status every 3 seconds (RUNNING → SUCCEEDED/FAILED)
     3. GET dataset items when status = SUCCEEDED
   
   Python Client: apify-client 1.7+
     ApifyClient(token).actor("apify/instagram-comment-scraper").call()
   
   Response Data:
     - text: Comment text
     - ownerUsername: Commenter handle
     - likesCount: Engagement metric
     - timestamp: ISO 8601 datetime
     - caption: Original post caption
     - videoViewCount: Reel view count
   
   Limitations:
     - Not real-time (scraping takes 10-30 seconds)
     - Rate limits enforced by Instagram (handled by Apify)
     - Free tier: Limited actor runtime hours/month
   
   Cost: Pay-per-use (actor compute time)

3. AT PROTOCOL (Bluesky)
   Provider: Bluesky Social (Decentralized)
   Package: atproto 0.0.55+
   Authentication: Handle + App Password
   
   Why AT Protocol:
     - Official Bluesky SDK (not web scraping)
     - Decentralized architecture (like ActivityPub/Mastodon)
     - Direct API access (no rate limits like Twitter API v2)
   
   Authentication Flow:
     Client.login(handle, app_password)
     Returns: Session token (handled internally by SDK)
   
   API Methods Used:
     - com.atproto.identity.resolve_handle()
       Purpose: Convert @handle.bsky.social → DID (decentralized identifier)
       Returns: "did:plc:abc123xyz"
     
     - app.bsky.feed.get_post_thread()
       Purpose: Fetch post + nested reply tree
       Parameters: uri (at://did/app.bsky.feed.post/rkey), depth=10
       Returns: Nested thread object with recursive replies
   
   Data Structure:
     - Post: Text, author (handle, display name), like_count, repost_count
     - Reply tree: Recursive structure (reply.replies[0].replies[...])
   
   Flattening Logic: Custom recursive function flatten_replies()
     Walks tree depth-first, extracts all replies into flat list

4. UPSTASH REDIS (Serverless Cache/DB)
   Provider: Upstash.com
   Type: Redis-compatible key-value store
   Access: REST API (no TCP connection required)
   
   Why Upstash (Not Self-Hosted Redis):
     - No Docker container to manage
     - No persistent TCP connection (stateless HTTP)
     - Free tier: 10,000 commands/day
     - Automatic scaling and backups
     - Perfect for serverless architectures
   
   Authentication: Bearer token in HTTP headers
   
   Commands Used (REST endpoints):
     - GET /get/<key>
       Purpose: Check if alert already exists
       Returns: {"result": "value"} or {"result": null}
     
     - GET /set/<key>/<value>
       Purpose: Store alert hash
       Optional: /set/<key>/<value>?ex=86400 (TTL in seconds)
     
     - GET /incr/<key>
       Purpose: Increment daily alert counter
       Returns: New count value
     
     - GET /exists/<key>
       Purpose: Boolean check for key existence
   
   Use Cases in Project:
     - Alert deduplication (key = "alert:<sha256_hash>", TTL = 24h)
     - Daily metrics (key = "stats:negative_alerts:YYYY-MM-DD")
     - Potential: Rate limiting, session caching
   
   Graceful Degradation:
     - If credentials missing: All methods return None/False
     - App continues working with in-memory state only
     - No crashes or errors

TROUBLESHOOTING:

Issue: "No comments found"
  Causes:
    - Comments disabled on video/post
    - Invalid URL format
    - API quota exceeded (YouTube)
    - Private/restricted content
  Solution: Check stderr output in debug expander

Issue: "Jira ticket creation failed"
  Causes:
    - Invalid project key (JIRA_PROJECT_KEY in .env)
    - Issue type doesn't exist in project
    - Insufficient Jira permissions
  Solution: Verify credentials, check Jira project settings

Issue: Redis deduplication not working
  Causes:
    - UPSTASH_REDIS_REST_URL/TOKEN missing
    - Network connectivity to Upstash
  Workaround: App continues working without Redis (no deduplication)

Issue: Analysis very slow
  Causes:
    - Large dataset (>500 comments)
    - Gemini API calls enabled (adds 1-2s per call)
  Solution: Limit max comments in ingestion scripts, disable Gemini

APPENDIX: ALGORITHM DETAILS
================================================================================

VADER SENTIMENT ALGORITHM:

1. Tokenization: Split text into words
2. Lexicon Lookup: Match each word to sentiment score
3. Negation Handling: Flip polarity if preceded by "not", "never", etc.
4. Intensification: Amplify score if preceded by "very", "extremely"
5. Punctuation: Add boost for "!" (excitement) or "?" (uncertainty)
6. Capitalization: CAPS = shouting = stronger sentiment
7. Emoji Mapping: 😊 = positive, 😠 = negative, etc.
8. Normalization: Scale to -1 (most negative) to +1 (most positive)

Example:
  "This is NOT good at all!!!"
  - "good" = +0.3 (lexicon)
  - "NOT" = flip polarity → -0.3
  - "!!!" = boost magnitude → -0.45
  - Compound score: -0.6 (Negative)


TF-IDF SPAM CLUSTERING ALGORITHM:

1. Corpus: List of spam-flagged comments
2. Tokenization: Split into words, remove punctuation
3. Stop Word Removal: Filter "the", "a", "is", etc.
4. Term Frequency (TF): Count word occurrences per comment
   TF(word, comment) = count(word in comment) / total_words(comment)
5. Document Frequency (DF): Count comments containing word
   DF(word) = number of comments containing word
6. IDF Calculation: Weight rare words higher
   IDF(word) = log(total_comments / DF(word))
7. TF-IDF Score: Multiply TF × IDF
   High score = word is common in this comment but rare overall (distinctive)
8. Vectorization: Each comment → vector of TF-IDF scores
9. Cosine Similarity: Measure angle between vectors
   cos(θ) = dot_product(vec_a, vec_b) / (||vec_a|| × ||vec_b||)
   Result: 0 (orthogonal/different) to 1 (parallel/identical)
10. Clustering: Group comments where similarity > 0.85 threshold

Example Cluster:
  Comment A: "Buy cheap followers at bit.ly/abc"
  Comment B: "Buy cheap followers at bit.ly/xyz"
  Similarity: 0.92 (highly similar spam campaign)


BURST DETECTION ALGORITHM:

1. Parse Timestamps: Convert ISO 8601 strings to datetime objects
2. Time Windowing: Group comments into 10-minute buckets
   Example: 12:00-12:10, 12:10-12:20, etc.
3. Count per Window: Number of comments in each bucket
4. Statistical Analysis:
   - Mean (μ): Average comments per window
   - Standard Deviation (σ): Measure of spread
5. Z-Score Calculation: Standardize each window's count
   Z = (window_count - μ) / σ
   Z > 0: Above average activity
   Z < 0: Below average activity
6. Outlier Detection: Flag windows where Z > 2.5
   Interpretation: Activity 2.5+ standard deviations above normal
7. Burst Flag: True if ANY window exceeds threshold

Example:
  Normal activity: ~10 comments per 10-min window
  Burst window: 45 comments (Z = 3.2) → FLAGGED


PRIORITY SCORING FORMULA:

priority_score = MIN(100, sum of:
  + 35  if toxic_language
  + 25  if negative_sentiment
  + 25  if intent in [complaint, refund_risk]
  + 15  if spam_markers
  + 10  if intent == support_request
  + 10  if urgency_emotion
  + 10  if anger_or_frustration
  + 10  if like_count >= 25
)

Priority Level Mapping:
  70-100: Critical (immediate action required)
  45-69:  High (address within 24 hours)
  20-44:  Medium (address within 1 week)
  0-19:   Low (monitor, no action needed)

Business Rationale:
  - Toxic language: Highest weight (brand reputation damage)
  - Negative + complaint: Combined 50 points (customer churn risk)
  - High engagement: Amplifies visibility (viral risk)


CAMPAIGN RISK SCORING FORMULA:

risk_score = MIN(100, sum of:
  + 40  if similarity_score > 0.3  (30%+ spam is duplicated)
  + 30  if burst_detected == True
  + 30  if spam_ratio > 0.15       (15%+ of comments are spam)
)

Risk Level Interpretation:
  70-100: Critical (coordinated attack likely)
  40-69:  High (suspicious patterns detected)
  20-39:  Medium (elevated spam activity)
  0-19:   Low (normal activity)
